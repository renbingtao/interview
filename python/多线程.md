## 一、GIL（全局解释器锁）

### 1. 定义

GIL 是 CPython 解释器层面的互斥锁：**同一个进程内，同一时刻只能有一个线程执行 Python 字节码**。
底层线程仍然是操作系统真实线程，可被内核调度，但受这把解释器锁约束。

### 2. GIL 释放时机

1. **IO 阻塞时主动释放**：网络请求、文件读写、sleep、数据库等待等。这是 Python 多线程能够提升效率的场景。
2. 字节码执行达到时间配额（新版基于时间片）：触发线程切换，释放 GIL，其他线程竞争。
3. 部分 C 扩展（numpy 等）：C 代码中可以手动释放 GIL，此时计算可以并行。

### 3. 核心结论

- IO 密集场景：多线程有收益；
- 纯 Python CPU 密集计算：多线程无法利用多核，切换还会带来额外开销，优先选择多进程；
- ⚠️ 重要误区：**GIL ≠ 业务层的线程安全锁**。GIL 只保护解释器内部引用计数等底层结构，业务共享变量的复合操作依然存在竞态，仍然需要手动加锁。

## 二、threading 模块核心类与 API

### 2.1 Thread

两种使用方式：

1. 传入 target 函数（推荐）

```
import threading
import time

def task(msg: str):
    print(msg)

t = threading.Thread(target=task, args=("hello",), daemon=False)
t.start()
t.join(timeout=3)
```

>
> 关键点：`start()` 才会开启新线程；直接调用 `run()` 只是普通函数调用，不会新建线程。

2. 继承 Thread，重写 run

```
class MyTask(threading.Thread):
    def __init__(self, msg):
        super().__init__()
        self.msg = msg
    def run(self):
        print(self.msg)
```

常用属性、方法

- `daemon`：守护线程；主线程退出时，守护线程会被直接终止，不会执行优雅清理，不适合写文件、落库等业务。
- `join(timeout=None)`：阻塞等待线程结束；设置超时后，超时会直接返回，线程不会被中止，继续运行。
- `is_alive()`：判断线程是否存活。

### 2.2 Lock / RLock

- `Lock`：不可重入锁，同一个线程连续两次 `acquire`，直接死锁；
- `RLock`：可重入锁，`acquire` 的次数必须和 `release` 次数匹配。

```
lock = threading.Lock()
# 推荐上下文写法，自动释放锁
with lock:
    pass

rlock = threading.RLock()
with rlock:
    with rlock:
        pass
```

### 2.3 Semaphore / BoundedSemaphore

控制并发数量（初始值 = 同时允许的线程数），限流、资源池场景。

- `Semaphore`：release 不设上限，多 release 不报错；
- `BoundedSemaphore`：release 超过初始值抛 `ValueError`，用来暴露 release 写多的 bug。

```python
import threading

sem = threading.Semaphore(2)
with sem:        # 进入 acquire，退出自动 release
    pass
sem.release()    # ✅ 允许，可用并发数量 2 → 3

bsem = threading.BoundedSemaphore(2)
bsem.release()   # ❌ ValueError: Semaphore released too many times
```

### 2.4 Event

线程间简单信号开关，支持重置、反复使用。

```
evt = threading.Event()
evt.wait(timeout=None) # 阻塞等待set触发
evt.set()
evt.clear()
evt.is_set()
```

### 2.5 Condition

条件变量，锁 + 等待通知，适合生产者消费者模型。

```
cond = threading.Condition()

def consumer():
    with cond:
        while not ready:
            cond.wait() # 释放锁并阻塞；被唤醒后重新争抢锁
        # 业务逻辑
        cond.notify()
```

>
> 要点：wait /notify/notify_all 必须在持有锁的情况下调用；条件判断要用 while，防范虚假唤醒。

### 2.6 Barrier

屏障，等待指定数量线程全部到达屏障点之后，才一起放行。

```
barrier = threading.Barrier(4) # 凑齐4个线程
barrier.wait()
```

### 2.7 threading.local () 线程本地存储

变量绑定到当前线程，各个线程之间相互隔离。

```
tls = threading.local()

def work():
    tls.val = 100
    print(tls.val)
```

## 三、线程池：ThreadPoolExecutor

模块：`concurrent.futures`
业务开发优先使用，避免频繁创建销毁线程，控制并发上限。

```
from concurrent.futures import ThreadPoolExecutor, as_completed

def job(x):
    time.sleep(0.1)
    return x*x

# 上下文管理器，退出自动shutdown
with ThreadPoolExecutor(max_workers=4) as pool:
    # submit：提交单个任务，返回Future对象
    f = pool.submit(job, 2)
    print(f.result()) # result()阻塞获取结果，会抛出任务内部异常

    # map：按入参顺序返回结果
    res_iter = pool.map(job, range(10))

    # as_completed：按任务完成顺序遍历Future
    futures = [pool.submit(job, i) for i in range(10)]
    for fu in as_completed(futures):
        print(fu.result())
```

重点说明：

- Future：`result()`阻塞拿结果、`exception()`获取异常、`done()`判断是否完成；
- 内部队列无拒绝策略，任务堆积会持续入队；
- `shutdown(wait=True)`：等待已提交任务全部执行完毕；`wait=False`不再接收新任务，已有任务继续执行。

## 四、线程安全要点

1. 内置类型部分操作是原子（受 GIL 保护），例如 `list.append(x)`；
2. 复合操作不是原子：`cnt += 1`、`lst[0] += 1`，依然存在竞态，需要锁；
3. `queue.Queue`：自带锁和 Condition，原生线程安全，生产者消费者优先选用，不用自己手写 Condition。

```
from queue import Queue
q = Queue(maxsize=5)
q.put(1)
q.get()
```

## 五、高频坑点

1. 忽略 GIL，用多线程跑 CPU 密集计算，期望多核加速 → 改用 `multiprocessing` / ProcessPoolExecutor；
2. 把 `Lock` 当成可重入锁，嵌套 acquire 造成死锁；
3. 守护线程执行持久化业务，主线程退出直接被杀死，数据丢失；
4. 调用 `future.result()` 不捕获异常，子线程异常在主线程阻塞拿结果时抛出；
5. 条件判断使用 `if` 而不是 `while`，遭遇虚假唤醒；
6. 混淆 `start()` 和直接调用 `run()`。

## 六、选型参考

- IO 密集（HTTP、数据库、RPC 调用）：`ThreadPoolExecutor`
- CPU 密集计算：不使用 threading 多线程，选择多进程
- 简单一次性信号通知：`Event`
- 生产者消费者：优先 `queue.Queue`；复杂等待逻辑使用 `Condition`
- 并发限流、资源配额：`Semaphore`
- 多线程同步卡点，等待一批线程齐步执行：`Barrier`
