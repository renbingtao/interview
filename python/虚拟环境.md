# 虚拟环境

> 核心目标：**解决依赖版本冲突**。
> 同一个机器上，项目 A 要 `requests==2.20`，项目 B 要 `requests==2.31`，如果全局装，版本会互相覆盖。虚拟环境就是给每个项目一套独立的 `site-packages`。

## 一、基础原理

Python 安装的第三方包，默认放在**全局 site-packages**。
虚拟环境本质：

1. 创建一个独立文件夹；
2. 里面生成一份**指向本机原版 Python 解释器的软链接（Windows 是副本）**；
3. 自带独立的 `pip`、独立的 `site-packages`；
4. 激活环境后，`python` / `pip` 优先调用这个环境里的版本，包只会装到这个环境，不污染全局。

> ⚠️ 重点：**venv 不会拷贝完整 Python，只是链接解释器，只隔离包，不能隔离 Python 版本本身**。
> 想同时用 Python3.8 / 3.10 / 3.12，venv 做不到，要用 `conda` / `pyenv`。

## 二、主流虚拟环境工具对比

表格

| 工具 | 内置 | 能力 | 特点 |
| --- | --- | --- | --- |
| `venv` | ✅ Python3.3 + 自带 | 隔离依赖，不能切换 python 版本 | 标准库，无额外安装，轻量，面试最常考 |
| `virtualenv` | ❌ 需要 pip 安装 | 和 venv 差不多，更早出现 | 老项目用，现在优先 venv |
| `conda(miniconda)` | ❌ 独立安装 | **既能换 Python 版本，又能隔离包** | 同时管理 Python 解释器 + pip 包 + C 库（numpy、cuda 相关） |
| `poetry` | ❌ | 虚拟环境 + 依赖声明 + 打包发布 | 现代工程化，自动管理 pyproject.toml |
| `pipenv` | ❌ | pip + venv 封装，Pipfile | Pipfile 替代 requirements.txt，现在慢慢没落 |

> 下面主要讲官方内置 **venv**

## 三、venv 完整命令（跨平台区分）

### 1. 创建虚拟环境

```bash
# 在当前目录，创建名为 .venv 的虚拟环境（行业通用命名 .venv）
python -m venv .venv
```

执行之后生成 `.venv` 文件夹，目录结构：

```text
.venv/
├─ bin/        # Linux/macOS：python、pip、激活脚本
├─ Scripts/    # Windows：python.exe、pip.exe、activate.bat
├─ Lib/site-packages  # 这个环境的第三方包
└─ pyvenv.cfg  # 配置文件，记录来源的python版本
```

### 2. 激活虚拟环境

激活的作用：**修改当前终端的 PATH，优先使用.venv 里的 python 和 pip**

- Windows（cmd）

```bash
.venv\Scripts\activate.bat
```

- Windows（PowerShell）

```bash
.venv\Scripts\Activate.ps1
```

> PowerShell 默认有执行策略限制，报错可以：`Set-ExecutionPolicy RemoteSigned -Scope CurrentUser`

- Linux / Mac

```bash
source .venv/bin/activate
```

激活成功标志：终端提示符前面出现 `(.venv)`

### 3. 在激活状态下操作

```bash
# 安装包，只会装到 .venv/Lib/site-packages
pip install requests

# 导出依赖清单（传统方式 requirements.txt）
pip freeze > requirements.txt

# 从清单安装（别人拿到项目一键装依赖）
pip install -r requirements.txt
```

### 4. 退出虚拟环境（终端）

```bash
deactivate
```

退出后，PATH 恢复，回到全局 python。

### 5. 删除虚拟环境

**直接删除整个 .venv 文件夹即可**，没有别的卸载命令，非常干净。

> 不要提交 `.venv` 到 git！`.gitignore` 一定要写 `/.venv/`

## 四、重要细节和坑点

1. **pyvenv.cfg**
   里面有 `home = 原python路径`，记录这个虚拟环境绑定的解释器。**不要移动 .venv 文件夹位置**，移动后链接失效，环境直接坏掉，只能重建。
2. 区分：激活与否的本质
   只是**环境变量 PATH 的顺序变化**，不是什么沙箱、虚拟机。
   你不激活，依然可以直接指定解释器运行脚本：

```bash
# Windows
.venv\Scripts\python.exe main.py
# Linux/Mac
.venv/bin/python main.py
```

很多 IDE（PyCharm、VSCode）就是这么做的：选择解释器路径，不用手动敲 activate。

3. venv 无法隔离 Python 版本演示
   本机只有 Python3.11，用 venv 创建出来的环境，也只能是 3.11；
   想要 3.9 的环境 → venv 不行，pyenv /conda。
4. requirements.txt 的缺点

- 记录**所有包（包括间接依赖）**，版本锁死，跨平台容易出问题；
  现代方案：poetry /pdm 使用 `pyproject.toml`，区分直接依赖和子依赖。

## 五、venv vs conda 核心差异

1. venv：**绑定本机已有 Python 版本，只管理 pip 包**；底层还是 pip
2. conda：自带包管理器，Python 本身也是 conda 的一个包，可以任意安装不同版本 Python，还能管理非 Python 依赖（C 库、二进制包）

> 数据分析、深度学习、带 C 扩展的库优先 miniconda；普通业务脚本、web 项目用原生 venv 足够。

## 六、工程最佳实践

1. 项目根目录统一命名虚拟环境文件夹：`.venv`，写入 gitignore；
2. 团队协作：
   - 小项目：`requirements.txt`
   - 正规开源 / 后端项目：poetry /pdm + `pyproject.toml`
3. 永远**不要在全局环境装项目依赖**，全局只保留少量基础工具（pip、poetry 等）；
4. 不要手动拷贝 `.venv` 给别人，只传依赖描述文件，对方本地重新构建虚拟环境。

## 七、一句话总结

venv = 一个轻量、Python 内置的**依赖隔离容器**，给每个项目独立 site-packages，避免包版本打架；它不是虚拟机，不执行代码，也不能切换 Python 解释器版本。
